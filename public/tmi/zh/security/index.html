Security Policy

TMI (Token-Made Intelligence, formerly Token Forest) is a proprietary desktop application published by Poietic Studio. With every optional online feature off — the default — it makes no outbound requests. We take reports about its security and privacy behaviour seriously, especially anything that contradicts our published Privacy Notice.

Supported versions

Only the latest public release receives security fixes unless a release note states otherwise.

VersionSupported
Latest public releaseYes
Older releases / development snapshotsNo — please upgrade

Reporting a vulnerability

Please report suspected vulnerabilities privately:

  1. Preferred: GitHub → this repository → Security tab → Report a vulnerability (private vulnerability reporting).
  2. Email: contact@tokenforest.com.au with a subject starting [SECURITY] (a dedicated security@tokenforest.com.au inbox is activating before the first public release).

Please do not open a public issue for an unpatched vulnerability. Ordinary bugs and feature requests are welcome in the public issue tracker.

Do not include in any report: your AI tools' logs or databases, prompts, conversation or WeChat message content, source code, access/refresh tokens, API keys, Claude or ChatGPT sign-in credentials, WeClaw's config or sign-in files, or other users' leaderboard data. If we need artifacts, we will arrange a minimal, private way to share them.

What to include

  • TMI version and exact download filename (plus its SHA-256 if possible);
  • operating system and architecture;
  • clear impact description and reproducible steps or proof of concept;
  • the state of each optional online feature at the time — leaderboard Off / Paused / On (and the project showcase), auto price-table update, update check, WeChat link (and whether the running WeClaw was started by the app) — this is what tells us whether you were in default mode;
  • whether the issue has been disclosed anywhere else;
  • how you would like to be credited (or anonymity).

Please use only your own accounts and test data, and stop once the issue is demonstrated. Setting TOKENFOREST_NO_NETWORK=1 makes the app refuse every outbound request it would make and refuse to start the claude / codex CLIs, which our own test suite never starts either (WeClaw, a separate program, is not covered); TOKENFOREST_NO_KEYCHAIN=1 keeps it away from the OS keychain. Use them with a separate HOME so your real data is not touched.

  • Daily comic reception (2026-11-12): the local-only production agent or its reference/style/prompt files being bundled into a user build; a client calling a model to generate these comics or attributing production tokens to its user; downloads while reception is off, sending identity/chat/usage, following redirects or fetching outside the fixed https://tokenforest.com.au/comics/ path; accepting a traversal filename, an oversized or invalid PNG, or a hash mismatch; rendered remote text interpreted as markup. Production is in tools/comicstudio/, delivery only in src/dailycomic.py. Only reviewed finished images and whitelisted public fields may be exported. From 2026-11-22 the author's machine also has a painter that learns one style a day, a static local gallery and an hourly LaunchAgent that only the author installs, by hand; none of these ship, the app has no entry point to them, and client behaviour is unchanged; any of them reaching a user build is in scope.
  • Automatic model checks are off by default and share one switch across characters. Check now runs once. Turning automatic checks off allows an in-flight call to finish and skips the remaining models.
  • Autonomous discovery uses a closed list of public directions. Local interest matching may choose one of these directions. Sending the underlying chat memory, a private notebook entry, handwritten persona, name override, custom rule or free text of a custom research topic into a free-browsing prompt is in scope. Linking a public follow-up to a private note, a failed read or a page the model only named is also in scope. Book and music outings retain their existing user-selected inputs. Notes from those outings stay private even when merged into an earlier note.
  • An optional excerpt must match the body of a public page returned on that outing. Private errands do not create excerpts. The local rotation of a recurring public subject uses notebook dates. Changing the AI settings view must not grant tools. The Growth process never receives the DeepSeek secret.
  • Contextual chat feedback is private to the character, limited to fixed response choices and controlled by chat memory. Exposing it to a public browsing tool, deriving it from an assistant reply or quoted speech, or restoring it after that character's reset is in scope. Public method learning uses linked, confirmed reads from separate days and excludes private material. A cross-field trial uses an existing outing and its existing permissions.
  • A reported outcome may mark an existing private shared or personal note after a short excerpt matches a user message from the same day. Marking it from the assistant’s own words, leaking it to public browsing, or retaining outcome metadata on a manually edited note is in scope. Scope names must occur in the same user message as its supporting excerpt. Ordinary recall must never advance the report date. A source span must match the stated speaker. Its date belongs to the original message. Later recall must not alter the ordering of corrections or outcomes. Treating an obvious hypothetical, question or fragment of a denial as an observed result is in scope. A transferable judgment requires the character’s earlier position and a user-reported outcome. A stale consolidation must not recreate a manually removed judgment. These fields belong to private memory and are cleared by manual editing. A spontaneous personal hint uses a source-checked note from that character, within the existing two private recall slots. The hint must not restore faded details or displace full direct matches. It does not verify a new outcome or make private notes available to public browsing.

Known limitations (published, not vulnerabilities by themselves)

  • The installer's SHA-256 comes from the same GitHub release as the installer, so it does not defend against an attacker who controls that release; neither package is code-signed.
  • account.json keeps a plaintext copy of the leaderboard credentials for older builds that do not use the keychain.
  • On macOS, keychain writes pass the secret as an argument to the security command, briefly visible to other processes of the same user.
  • The signature on garden.json is tamper-evident, not tamper-proof.
  • The anonymous user ID is readable through the public database API; app version and previous ID are readable by any anonymous session.
  • Your row's public "updated" time reveals roughly when you sync.
  • The server's score-change log is kept after you turn the leaderboard off (administrators only).
  • While the claude or codex CLI runs for cLAudE or CodeX, the persona prompt (including her notes about you) sits in a 0600 temporary file in the data folder's brain/ (for CodeX, the reply too), readable by other processes of the same user during those seconds; it is deleted right after.
  • Codex tools are switched off only by the names the installed codex knows; a tool added in a newer codex and not yet on the app's list is not disabled, leaving the read-only sandbox and approval_policy="never" as the backstop.
  • The claude and codex CLIs are third-party programs you installed; they connect, update and keep state in their own way, and the app controls only the arguments, standard input and working directory it gives them. The "What she can do" limits rest on their permission and sandbox behaviour (claude's dontAsk mode and allow rules, codex's sandbox), which we retest before each release.
  • With "What she can do" on, what she reads, sees or finds (files, pictures, search results, pages) goes to Anthropic or OpenAI as part of the conversation; with "Read your files" on, cLAudE can read any file in your Desktop, Documents and Downloads; when cLAudE opens a link you sent, that site sees your IP address.
  • CodeX's image viewer (codex's view_image, left on with "See pictures, keep stickers") can open any picture path on the computer, because codex's sandbox limits writes, not reads; what it sees can only go to OpenAI and into her reply.
  • The drawing run (codex exec started by the draw tool) switches off every codex feature except image generation, the shell included, but only by the names the installed codex knows; a feature added in a newer codex stays on until the app's list catches up. With the shell off, codex saves the picture under <CODEX_HOME or ~/.codex>/generated_images/<thread id>/; the app reads the thread id from codex's --json output (hex digits and hyphens only), moves the newest .png from that folder into her drawings/ and deletes that one folder. If codex changes where it saves pictures or what --json prints, drawing fails rather than touching anything else. When no picture comes out, she gets only a failure category (quota, not signed in, not generated), never codex's own text.
  • cLAudE's drawings (from 2026-11-12) are SVG code written by her claude run; the app drops anything with scripts, external links, embedded images, foreignObject, a DOCTYPE or custom entities before saving it and renders it locally with QtSvg. An SVG that gets past that check and makes the renderer read a local file or reach the network is in scope. From 2026-11-22 BlueGiantFish draws the same way in her own time (SVG written by DeepSeek, same check).
  • "Let GPT draw for her" (from 2026-11-22, off by default, cLAudE and BlueGiantFish only): the description she writes in her own time goes through the drawing run above (same --disable list, shell off, lightest text model), falling back to her own SVG if it fails. She may write it after reading unfamiliar pages; using that run to make codex execute commands, read or write outside her drawings/, or send OpenAI anything beyond the description is in scope.
  • Files she writes herself in her own folder get the CLI's default permissions; the folder itself is 0700.
  • Shrinking pictures for sending uses macOS's sips; elsewhere large pictures cannot be sent. The original WeClaw does not pass incoming pictures on, so "See pictures" needs a modified WeClaw build.

An implementation that does not match these published descriptions is in scope.

Out of scope (usually)

  • UI, animation or layout bugs, including a wrong activity icon; feature requests;
  • token-count differences explained by our documented metric definitions;
  • problems in WeClaw itself (report them to https://github.com/fastclaw-ai/weclaw), in Tencent's WeChat services, or in the AI tools and APIs the app reads from or connects to — unless the way the app drives them causes the problem;
  • SmartScreen warning that a new file is "not commonly downloaded" when signature/hash are otherwise valid;
  • issues requiring full prior control of the user's OS account;
  • automated scanner output without demonstrated impact;
  • social engineering of team members.

We may still act on out-of-scope reports that expose real user risk.

Our response

Targets, not guarantees: acknowledge within 3 business days; initial assessment within 7 business days; status updates at least every 14 days for confirmed issues. For critical issues we may pull affected downloads immediately. Fixes are rebuilt from a clean commit, re-signed where applicable, republished with new checksums, and announced in the release notes; withdrawn binaries stay marked rather than silently rewritten.

If you act in good faith — avoid privacy harm, use only your own data, allow reasonable time to fix — we will work with you, and with your permission credit you in the release notes.

Privacy requests

Requests to delete a leaderboard entry, the anonymous account or the score-change log, or questions about data handling, are not vulnerabilities — see the Privacy Notice contact section. Never send anyone your tokens or API keys.

Release authenticity

Official downloads come only from the official website and this repository's Releases, each with a SHA-256 checksum and a stated signing status. See the download verification guide before running anything that fails verification.

When the in-app update flow downloads an installer, it checks it against the SHA-256 published in the same GitHub release. That detects a corrupted or tampered download; it does not defend against an attacker who controls that release. Neither the Windows nor the macOS package is currently code-signed, so your operating system cannot confirm the publisher to you. The app never installs an update by itself, never replaces itself, and keeps the downloaded file's quarantine / mark-of-the-web flag so your OS still runs its own checks. An implementation that does not match this (no checksum check, flags stripped, install proceeding after a failed check) is in scope.
